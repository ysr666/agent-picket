# Windows NTFS WAL 实际写入实验 · 2026-10-13

这是 Agent Picket 对真实 Windows 持久账本的下一步独立验证，但**绝不是已经具备生产安全保证的存储后端**。

`src/adapters/node/windows-ledger-writer.experimental.ts` 是刻意被 `package.json` 排除的研究模块，任何已安装的 DSH、Claude Code 或 Codex 插件都不能调用它。其 `ExperimentalNtfsWalWriter` 仅在 Windows 可实例化，使用既有 DurableStats v1 的 JSON 快照和逐行 HMAC-SHA256 WAL 结构，而不是创建不兼容的新账本。每个合成 tool-start 写入都要先确认受保护目录、受控文件清单和本进程锁身份，写入日志并 `fsync` 后才更新内存中的累计计数；恢复时通过 v1 只读重放模块确认签名、顺序和数据完整性，并恢复指纹去重集合。实验 API 只接收合成事件 ID，不用于拦截或记录用户对话。

安全范围严格受限：只自动创建全新、空的、受保护 NTFS 目录；现有旧锁、恢复锁、坏快照、受损 WAL、最后一条未完成日志均拒绝。只允许**没有未验证接管的正常 close→open**，不自动抢占死进程锁。没有实现 WAL checkpoint，硬性限制最多 255 条已确认记录；超过限制拒绝后续写入，避免无界日志增长或误称可生产使用。整个原型不进入 npm 包，不改变当前 `DurableStats` 在 Windows 上构造之前即拒绝的行为。

`tests/windows-ledger-writer.real.test.ts` 在真正的 Windows Runner 和临时私有 NTFS 目录上执行三个验收：

1. 新建真实账本、写两条带签名和 fsync 的记录、同 ID 去重、拒绝第二个同时取得锁的写入者；正常关闭后重新打开，确认序号/累计计数/去重不变，新增记录仍保持连续序号；通过独立 WAL 验证器复核，再验证完整日志记录被篡改时拒绝写入且保留坏日志原文。
2. 启动独立 Node 子进程，写入并 fsync 一条记录后强制终止进程；锁必须保留，下一写入者必须拒绝接管，但独立只读重放仍能验证已经确认的计数未丢失。
3. 在非 Windows 系统上，即使存在合法路径也不允许误启用该实验性 NTFS 写入器。

**仍需验收：** 一次性锁创建后文件句柄与 NTFS DACL 检查之间的 TOCTOU、跨进程死锁身份比较及原子删除、Windows 上已打开文件的 checkpoint/原子替换、真实完整 `DurableStats` 功能和所有被跳过的 Windows 测试、实际安装的各 Host×OS 兼容矩阵。任何已验证的“独立实验写入”都不等于“可以让工会真实罢工”；1.0 发布闸门继续 NO-GO。

## 2026-10-13 · 手动检查点与精确崩溃窗口实验

实验写入器新增**显式且仅用于测试**的 `checkpointForTest()`，不自动后台运行，也不进入 npm 包。它在受控锁和私有 ACL 验证后，将现有 v1 密钥、连续序号、累计次数、UTC 每日次数和最多 16384 个去重指纹写入新的快照临时文件并 `fsync`，验证 NTFS 文件 ACL 后以原子重命名提交快照。然后新建并同步空的 WAL 临时文件，**先关闭原 WAL 文件句柄**，再替换旧 WAL，验证目标权限并重新打开追加句柄。

在快照提交与旧 WAL 替换之间若进程崩溃，**旧 WAL 必须保留**；独立 v1 只读重放器应按快照序号跳过已确认旧记录，不重复累计工时。异常终止产生的旧锁也必须保留，实验原型不能自动抢锁。手动检查点后的干净关闭与重开，必须同时保持总次数、逐日次数、去重指纹和连续序号。已添加两项独立的 Windows 专项 E2E：正常检查点→新 WAL→重新打开→去重→再次检查点，以及子进程在快照 `fsync`/重命名后通过精确测试回调停住、父进程强制终止并验证旧 WAL 完整保留和零重复重放。

此原型依然 **不是生产 Windows DurableStats**：检查点需要测试 API 手动触发，每段 WAL 最多 255 条，指纹集合最多 16384 项；NTFS 检查与真实文件句柄之间仍有 TOCTOU，安全的死锁接管、强制断电及 DSH/Codex/Claude 正式适配仍未验收。Windows 正式统计功能继续在 `mkdirSync` 之前拒绝启用，1.0 发布闸门必须保持 NO-GO。

## 2026-10-13 · 文件句柄身份复核（仍非原子安全证明）

新增只在 Windows 有效的实验辅助函数 `verifyNtfsOpenFileIdentity(fd, path)`：同时读取 `fstat` 与 `lstat` 的真实文件类型、设备 ID、NTFS inode/file-index 以及硬链接数；若不支持文件 ID、路径被替换、路径不存在、链接数量异常或任一调用失败，统一 **fail closed**。实验写入器在初次打开 WAL、每次追加事件、创建检查点前以及检查点替换 WAL 后都会检查已打开句柄是否仍对应经过检查的路径。新增真实 Windows 专项测试，验证正确打开的文件获识别，而将相同句柄与另一文件或不存在的路径比较会被拒绝。

注意：两次系统调用之间仍存在竞争窗口；这只是削弱了“检查 A 文件、写入 B 文件”的风险，不是锁定内核对象与 ACL 的不可分割事务。实际安全上线还需要 Windows handle-based 防重解析检查、DACL 与句柄对象绑定、完整锁接管序列及多进程压力测试；所有实验模块继续排除在发行包外。

## 2026-10-13 · 独立双进程抢锁回归

先前原型已验证同一 Node 进程中的第二个写入对象无法夺锁。新增一项真正的**两个 OS 进程**验收：父进程持有已 fsync 的私有 NTFS WAL，另起一个 Node 子进程尝试构造同路径的实验写入器。子进程必须明确返回“第二写入器拒绝”，且退出码为 0；它不能修改锁或日志。父进程随后还能追加并确认两条记录，正常关闭后独立只读恢复必须显示连续序号 2、累计工具调用 2。此项仍属于源代码/隔离实验，不代表正式多 Host 同步、跨进程死锁恢复或 Windows DurableStats 安全支持。


## v1 原有统计字段必须完整保留

专项审查发现原型最初仅保留 `toolCalls`，检查点时会把已有 v1 文件中的 `turnStarts`、`turnEnds`、`toolResults`、`completedTurnMs`、`checked/safe/review/targeted` 等字段归零。这不符合与 `DurableStats` v1 兼容的承诺，也构成潜在信息丢失。已修复为保留**所有**原始计数字段和每日字段，重放 WAL 时对所有合法 `changes` 字段按既有格式恢复；实验性新事件只增加自己的工具调用计数。新增真实 Windows 专项测试，以事先写入多种非零累计/每日计数的标准 v1 合成快照为输入，执行新工具事件→检查点→重新验证，确保任何既有计数字段都不会被静默清零。仍不得将该实验模块投入生产或对用户旧账本自动迁移。


## 2026-10-13 · 既存 WAL 缺失与 v1 指纹容量边界

复核确认了一个可能导致**已确认计数静默消失**的情形：旧实验写入器打开已有 v1 快照时，如果 `aggregate.v1.journal` 不存在，会将其视为空日志，随后使用带自动创建能力的追加模式重新建 WAL。若真实 WAL 曾存有尚未检查点化的记录，其累计值与去重记录会就此不可恢复。现在**只有全新受保护目录**的初始化流程能使用 `wx` 创建新 WAL 并 `fsync`；已有目录必须有可验证的私有 WAL，追加句柄和检查点替换后的重新打开均采用不带 `O_CREAT` 的 append 模式。缺失时拒绝写入且不补造文件；NTFS 只读检查也返回 `unconfirmed` 而不是虚假的 `verified`。新增真实 Windows 原生反向测试，用隔离的、已经写入并 fsync 的合成记录模拟 WAL 删除，并验证旧快照不变、文件不会重建、锁仅释放本进程新取得的部分。

另一方面，`DurableStats` v1 的事件去重指纹是**按插入顺序滑动保留最新 16384 个**，不是“填满 16384 后永久停写”或“重放 WAL 后无限增大”。现在实验写入器与纯只读 HMAC 重放器按相同的有界 FIFO 语义处理已签名的 WAL；检查点始终不能写出超过 v1 容量的指纹集合。新增跨平台协议测试和 NTFS 上预置满额合法 v1 快照 + 带签名 WAL + 新事件 + 手动检查点 + 冷重开验收。

**严格限制：** 现有 WAL 文件即使存在，也可能被同权限主体替换成看似合法的空文件；若没有外部持久认证的提交水位，这种回滚无法仅凭旧快照和空 WAL 证明未丢数据。本修复不将 TOCTOU、掉电 fsync、完整生产 `DurableStats` 或跨进程重启安全声称为已解决。所有代码仍为独立实验性研究，Windows 生产后端仍在构造前 fail-closed，1.0 NO-GO。

## 2026-10-13 · 独立已确认序号水位实验（仅新建实验账本）

复现了 v1 的一个结构性事实：WAL 最末端如果删除了**完整而有效、已经签名并 fsync 的一条记录**，原只读 HMAC 重放可能把剩余的前缀判为 `verified`，却静默降低工具工作计数；仅有一个快照加一个日志无法证明“没有遗漏已确认后缀”。

新增实验性 `aggregate.v1.anchor` 水位文件和纯校验模块 `windows-wal-anchor.experimental.ts`。仅全新隔离 NTFS 实验账本由原型自动创建独立的水位 0；每次合成工作事件先写入 WAL 并 fsync，再将 `{version,sequence,toolCalls,tipMac}` 以私有临时文件 fsync 后重命名提交，最后才向调用方返回成功。恢复时必须同时比对原 HMAC 重放的最终连续序号、工具工作计数，以及 WAL 最后一条签名记录的 MAC（若新记录尚未合入快照）。WAL 尾段即使整条删除、日志仍有合法 JSON/HMAC，水位不符也必须拒绝继续写入并保留现有字节。原水位丢失同样拒绝重开。

新的测试覆盖：跨平台完整 WAL 与合法截断后的差异、合法检查点后的空 WAL、快照已经提交而旧 WAL 仍存在的中间阶段、坏水位格式、真实 NTFS 上删除已确认完整后缀及随后恢复原文件，以及 WAL 已 fsync 但水位尚未提交就人为中断导致的“未被确认却已有 WAL 字节”状态。最后一种状态必须停机等待审查，绝不能把日志重建为空。原本所有手工预置既有 v1 快照的专项测试都**仅在合成测试夹具**内显式补建水位；这绝不证明任何真实旧 v1 账本历史没有丢失。

**重要限制：** 这个侧车水位不是有独立信任根的不可篡改证明。同权限、可修改三个文件的攻击者仍能将快照、WAL 和水位一起回滚。NTFS 重命名后的目录持久性、DACL/文件句柄 TOCTOU、多进程活锁恢复、掉电、真实 `DurableStats` 所有事件家族、老 v1 账本无损迁移和 Host 安装验收均未完成。原生产 `DurableStats` 仍在 Windows 写入任何文件前拒绝启动。本实验模块和 `.anchor` 文件不允许进入 npm 安装包：已增加 `package.json` 的显式排除并用干跑归档清单核对。

## 2026-10-13 · 原生 Windows 水位审计入口与真正 SIGKILL 崩溃复测

针对原有 `inspectPrivateNtfsWalReplay()` 的命名易产生歧义：它仅保证现有 v1 快照与**剩余** WAL 的格式和签名自洽；即使已确认的整条末尾记录被删掉，旧的 v1 检查仍可能返回 `verified`。新建、仅供研究的 `inspectPrivateNtfsAnchoredWalReplay()` 明确只用于带独立水位的实验账本；要求 NTFS 私有目录验证、无活动/恢复锁、全部三份文件存在、合法 v1 重放和独立水位二次比对。缺少或损坏水位、已确认后缀回退、非 NTFS 或检查期间发现锁，一律返回 `unconfirmed`，**绝不尝试用缺失的水位自动补证真实旧 v1 账本**。它是只读的尽职调查接口，不能用于授予可写权限；路径读取与 ACL/DACL 并非原子事务。

新增 Windows 专项反向断言，严格区分旧 v1 检查器的“剩余签名有效”和新水位检查器的“已确认记录未缺失”；还加入一个真实独立 Node 进程先 fsync 两条合成 WAL 记录、仅将首条提交到水位、通过测试回调暂停，再由父进程实际 `SIGKILL` 的崩溃窗口测试。预期旧 v1 仍能读到两条，但水位只确认一条，读写均拒绝自动恢复；崩溃锁原封保留，已存在的日志字节不得被截断或重写。所有新增文件继续排除安装包。生产 Windows 账本仍严格 NO-GO。

## 2026-10-13 · 更正精确崩溃测试的同步边界

代码对抗审查发现一个此前被自动化测试通过状态掩盖的问题：原先 `checkpointForTest` 的 Windows 子进程回调以及新加的 WAL 水位回调使用 `process.stdout.write(...); setInterval(...)` 作为“停住”的标记。但是 `setInterval` 仅安排未来执行，**不会阻塞当前回调**；原始测试可能在父进程收到标记前已经执行了后续 WAL 替换或水位更新，先前的 PASS 因而不足以证明它命中的具体崩溃窗口。已经将两处测试改为同步 `writeSync(1, marker)`，立即在同一回调内 `Atomics.wait()` 阻塞主线程，再由父进程强制终止。新加一项**可在三系统运行**的测试，证明这个同步标记发出后绝不会提前执行标记之后的代码。

更正前已通过的 Windows CI 不应当再被当作“精确强杀窗口已验收”的证据；须以本次修改后的 Windows 原生 CI 结果为准。这个改动没有启用自动接管或改变正式数据后端，安全发布闸门保持 NO-GO。

## 2026-10-13 · 完整逻辑状态水位 v2：禁止非 toolCalls 字段和去重记录回滚

对独立水位进一步审查发现最初 `{sequence, toolCalls, tipMac}` 只能绑定工具计数与有签名 WAL 的最新位置，却**不能**保护既有 v1 快照中的 `turnStarts/turnEnds/toolResults/completedTurnMs/checked/safe/review/targeted`、`daily`、`seen` 指纹集合和 HMAC secret。只改动快照中这些字段，旧 v1 仍可能返回 verified，新水位 v1 也会误报已确认状态完整。

**实验侧车协议升级为 v2，拒绝缺字段或旧版 v1 侧车**（不自动迁移）。研究用只读 HMAC 重放增加一个不泄漏原始内容的 43 字符 SHA-256 `stateDigest`，基于重放后的规范化逻辑状态：连续序号、密钥、全部九项累计计数、按日期排序的逐日九项计数、保留顺序的有界指纹集合。没有把用户原始事件 ID 放进外部凭证。实验写入器只能在 WAL fsync 后重新读取并验证快照+WAL，计算完整重放结果，确认序号和 toolCalls 相符，然后将状态摘要连同水位写入私有临时文件、fsync 并重命名，才返回成功；失败仍 fail closed。新只读带水位检查器比对重放摘要，拒绝任何只改动快照其他计数、逐日统计、指纹或 secret 的回滚。

规范化语义要在手工 checkpoint 前后保持不变（已签名旧 WAL 留存与新空 WAL 两种窗口），否则安全崩溃窗口会被误拒。增加跨平台纯协议测试和真实 Windows NTFS 快照字段逐项篡改反向验收；合成旧 v1 测试夹具只能由测试代码**显式**构造 v2 侧车，绝不作为真实用户旧账本的迁移手段。此 SHA-256 仅是侧车绑定指纹，**不是**异地不可篡改账本；同权限联合替换快照、WAL、水位三份文件仍能伪造整体回滚。物理断电、磁盘缓存、目录重命名持久性、原子 ACL/Handle 和多 Host 恢复问题没有因此得到解决。

## 2026-10-13 · 锁文件句柄驻留与同 token 换锁反向验证

进一步审查发现实验写入器原本在创建并 `fsync` 锁后立即关闭句柄，之后只检查路径对应文件内容的随机 token；如果具备修改权限的另一进程将锁文件替换为**相同 token、不同 NTFS 文件 ID**的副本，仅验证 token 无法发现文件替换。原型现在保留 `wx` 创建的原始锁句柄直至正常关闭，首次开启、每次工作事件追加、每次测试检查点都额外以 `fstat/lstat` 核对该锁句柄与当前锁路径的 NTFS device / inode (file index) 和硬链接数。关闭时先记录原始文件 ID，释放持有句柄，再对即将删除的锁进行文件 ID、私有 ACL 与 token 比对；如果路径已被替换，**不允许删除别人的锁**。

新增原生 Windows 替换锁文件测试：真实写入器保持锁句柄，外部测试代码创建**完全相同 token** 的不同文件，尝试用原生 rename 替换当前锁。若 NTFS 因原文件正被持有而拒绝替换，必须确认原始写入和正常释放仍可继续；若替换在当前文件共享语义下成功，下一次工作事件必须在追加任何 WAL 字节之前拒绝，新锁副本不能被旧拥有者的 `close()` 删除，且后续新写入者因不确定旧锁而拒绝抢占。所有文件、事件与令牌仅在临时合成 NTFS 测试目录中，不接触真实用户数据。

**这依然不是内核原子的所有权证明**：检查文件身份和实际 `writeSync`、`renameSync`、`unlinkSync` 是分开的 OS 调用，两次检查间仍有替换竞争；释放句柄到删除锁之间也有窗口，且 Windows ACL 和文件 ID 并不构成事务。真正生产支持仍需要 handle-bound ACL/security descriptor 和单内核对象的 owner fencing/lease recovery，不能仅靠此实验开锁或恢复死锁。1.0 NO-GO。
