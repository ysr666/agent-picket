# Windows private ledger NTFS security probe — experimental, NOT storage support

Agent Picket's `DurableStats` deliberately requires UNIX `0o700` directories and `0o600` single-link regular files. Windows `fs.stat().mode` cannot prove private NTFS ownership and DACL security; treating that numeric mode as POSIX would leak private pseudonymous work metadata. The Windows persistent ledger must remain FAIL-CLOSED until a complete owner-only native implementation is independently accepted.

`src/adapters/node/windows-private-acl.ts` introduces **READ-ONLY** `verifyPrivateNtfsAcl` for research, without modifying a user's permissions or writing any data. It rejects unsupported platforms, missing paths, symbolic links, multi-link files, unexpected owners (directories require the exact user SID; elevated-token files may also be owned by builtin Administrators only if the current user has Modify rights and every Allow ACE remains trusted), inherited directory ACLs, ANY allow ACE outside current-user/SYSTEM/built-in Administrators, and missing owner modify rights. An isolated encoded Windows PowerShell/.NET file-security API script reads the actual Windows security descriptor by SID (without Get-Acl/Set-Acl module autoloading), never interpolates a user path as source code, runs without elevation and returns a fixed verdict. Unexpected output, process failure or timeout means `false`. No production adapter currently calls it; installing Agent Picket does not automatically invoke PowerShell or modify an ACL.

`tests/windows-private-acl.test.ts` adds opt-in Windows-native checks: a normal inherited temporary folder is not accepted as private; a disposable folder with an explicit, test-only protected DACL granting only current user, SYSTEM and administrators is accepted; a newly created file inheriting that trusted ACL is accepted; and adding an explicit `Everyone` read ACE makes the verification fail. Test fixtures are synthetic, automatically deleted, and never include user prompts, tokens or sessions. Windows CI uses this suite as portable/core work only; it is NOT a certificate that existing persisted data, lock files and atomic snapshot writes are race-free on NTFS.

Next release-blocking requirements: a race-resistant private Windows directory initialization workflow, reparse-safe parent/open handles, protection of every snapshot and journal/lock file, cross-process mutex and dead-PID recovery, deletion and crash-consistent persistence under actual DACLs, and full unskipped Windows `DurableStats` tests. Do not remove Unix-mode checks on Windows or skip privacy checks to make tests green. No GO for 1.0 until independently verified.

## Follow-up: new empty private-directory creation experiment

`createProtectedNtfsDirectory(path)` is a separate, **not shipped** Windows-only experiment. It refuses existing paths; it never changes an existing user's ACL. For a brand-new empty directory only, it sets a protected, non-inherited NTFS DACL permitting the current user, SYSTEM, and built-in Administrators, using supported .NET directory security APIs. It requires immediate readback through `verifyPrivateNtfsAcl` before reporting success, and never stores any prompt, session or work count. On a failed setup it may remove its own *empty* new directory but will not recursively delete uncertain files. An additional native Windows CI case checks creation, directory and newly inherited file ACL, and refusal to overwrite existing directories.

This deliberately does **not** activate a Windows `DurableStats` instance or imply that reparse-safe multi-directory ancestors, runtime file replacement, WAL checkpoint, lock stealing, process-crash handling or cleanup are complete. Treat it as preparation only. Windows release remains NO-GO.


## Read-only ledger layout preflight and real NTFS file-lifecycle regression

`src/adapters/node/windows-ledger-layout.ts` adds `inspectPrivateNtfsLedgerLayout(directory)`, a strict **read-only** probe excluded from the installable package. It refuses unsupported OSes, symlink/junction path ancestors, directories without protected user-owned DACL, unexpected filenames, and any existing snapshot/WAL/lock/recovery/temporary file whose file ACL is not private. It checks every known file; checking the directory alone is not sufficient. A positive verdict does **not** grant permission to instantiate `DurableStats`, because open-handle identity and rename/ACL races still need review.

`tests/windows-ledger-layout.test.ts` exercises the real NTFS filesystem on the ephemeral Windows CI runner: securely creates an empty synthetic ledger directory, writes a snapshot temporary file using exclusive creation and fsync, atomically renames to the snapshot, appends and syncs synthetic journal text, creates an exclusive lock and verifies duplicate-lock creation fails. The layout must remain private at every step. It then uses `icacls` solely on its OWN fixture to grant Everyone read access to the journal and verifies the entire layout fails closed; a separate unknown-file fixture is rejected. No user work, secret, raw prompt or source session is touched.

Future prerequisites remain handle-based identity verification, ancestor reparse checks during actual open, race-resistant file replacement, dead-process lock recovery and power-failure WAL replay before real Windows storage can be enabled. Release remains NO-GO.

The native lifecycle suite also verifies a **second atomic replacement**: checkpoint compaction creates a new private temp and renames it onto an already-existing WAL journal, then rechecks the resulting ACL. This targets Windows rename/replace semantics, which differ from POSIX in some open-handle cases; the fixture closes the old journal first, so active concurrent handles still need separate testing.

## Production fail-closed: no speculative Windows directory creation

`DurableStats` itself now refuses unsupported Windows persistent storage *before* calling `mkdirSync` or touching snapshot/WAL/lock paths. This closes a side effect in the previous implementation where Windows could create an inherited-ACL directory and only afterward reject its POSIX mode. The native `tests/windows-durable-fail-closed.test.ts` verifies a rejected constructor creates **neither the intended ledger path nor its parent**. This guard is intentionally distinct from the experimental, excluded NTFS layout probes; Windows production stats remain NO-GO until all file-handle/locking/recovery requirements are fulfilled.
