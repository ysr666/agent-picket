## 2026-10-12 · Host 回执与界面订阅异常隔离

发布审查发现一个可复现的错误（修复前两条专门回归测试均失败）：`client-bargaining` 和 `client-lifetime` 在通知浏览器 UI 订阅者时，未隔离单个监听器的异常。某个已经卸载、抛错的 UI 组件可能把**已经成功写入 Host 的工会案件/举牌**向调用方误报为失败，或者阻止工时加载状态从 `loading` 进入 `available`，并吞掉后续订阅者的更新。这会诱发用户重复点击、重复操作，不是装饰性体验问题。

现在两处浏览器侧通知均逐个隔离监听器错误，真实 Host CAS、会话绑定、授权、账本格式、消息提交与原有单击象征性行动均不改变。增加了已确认 Host 写入、另一个健康订阅者仍收到信号、7→30 天工时刷新与无多余网络请求的回归。该修复不能替代真人可用性验收或第三方安全审计。

## 2026-10-12 · Host 授权撤销与组件卸载完整性加固

本轮用三个修复前已经失败的回归检查发现既有生命周期风险，并在 1.0 候选中修复：

1. 官方 Host 工会授权已明确 OFF 时，CLI /union strike、/union resume 曾静默回退到旧本地象征性仪式并反馈成功（包括用户主动关闭工会以后）。现按 Host 显式授权判定为不可用，不写工会账本、不拒绝真实模型请求；正式插件若没有可验证的 Host Settings Owner，也必须明确拒绝象征性行动；只有不作为发行入口的独立核心研究模拟器保留旧本地演示能力。
2. Web 工会控制器 dispose() 原本只注销订阅和清除 Session 键，遗留组件回调仍可在卸载后重新 setActiveSession 并操作 Host。现不可逆记录销毁状态，禁止重新订阅、重新绑定 Session 和发起任何账本写入。异步旧 Session 哈希继续采用现有 epoch 防串号。
3. 原 /union snapshot 即使具有真实 Host 工会服务也只读取旧的 SymbolicUnion 内存标记，可导致 CLI/Web/机器可读快照相互矛盾，甚至在 Host 关闭工会后投影出旧本地举牌。现 Host 账本存在时只依据 Host 授权与 picketStatus 返回状态；Host 未证明可读时清空象征性动作投影，不臆造行动时间。未接入官方 Host Owner 的旧独立 Demo API 维持其既有只读行为。

正常首次明确授权一次、象征性行动单击执行的规则完全不变；旧模拟权限绝不自动升级为真实拒绝权限。真正任务阻断仍为 OFF。本轮不要求每次确认，没有增加任何 UI 功能。

## 2026-10-12 · 尊严计数接口出站白名单和撤销后重新授权刷新

审查原始源码和已安装包时，找到三条**预修复测试实际失败**的隐私/生命周期问题：

1. DSH Host 尊严计数 Fetch 路由原先直接 Response.json(lookup(key))。生产默认计数器当前只生成结构化数值，但如果上游对象意外混入原 Session ID、原始 prompt 或附件元信息，会被原样序列化返回。现在 Host 出站口逐字段验证十个允许字段、计数平衡、来源和非阻断声明，并重新构造精确十字段响应；字段污染被剔除，畸形计数直接拒绝为 503，而不是把任何额外字段送入浏览器。此项与浏览器端已有的严格输入校验属于不同安全层。
2. lifetime-work 浏览器读取器如果通过后台 refresh 首先发现 Host 授权撤回，之前只清除显示而保留旧 Session/permission 绑定；用户重新授权同一 Session 且未插入 React snapshot 时会跳过新的 Fetch。现在在此路径同步清除 Session 与授权绑定，再授权必须重新读取 Host。
3. dignity 浏览器读取器的同类刷新路径也未清除 Session，导致重新启用原会话时无法再次 Fetch。现在一起修复，并保护 dispose 后的订阅/会话绑定。

均沿用现有 Host 单次知情授权、撤销后不再读取敏感摘要、只读真实 Host 计数、不上传原文、不引入额外界面确认的合同。未增加任何产品功能，也不证明真实拒绝任务 #80 已可安全开启。

## 2026-10-12 · 第三轮发布安全复核：Host 写入回执、卸载回调和有限留存

本轮优先核查真正可能造成“已成功写入却提示失败”、卸载后继续更新，以及历史数据范围被误导的风险，而不是新增产品功能。

- **官方 Host 设置回执通知已修复**：原 createOfficialDsh017Scope.subscribe() 直接调用第三方 UI listener。一个旧 React listener 抛错，会反向污染已经成功的 Host CAS 回执流程，让首次授权或撤销操作误报失败并中断下游 UI 同步。本轮在真实 Host 设置镜像适配边界逐个隔离订阅异常，不改变 Host 的 mutate、revision 校验、readback 或拒绝逻辑；修复前单独复现测试失败，修复后通过。
- **已卸载工时读取器无法复活**：旧 createBrowserLifetimeWorkReader 卸载后仍允许遗留界面 callback 重新订阅；再调用 refresh() 会对已销毁组件继续发事件。现在卸载后订阅、新绑定、刷新一律无效；已在测试里验证新的网络请求不会发生、也不会通知过期订阅者。真实正常授权读取路径不变。
- **跨标签页写入审查**：真正防止旧数据覆盖新数据的是官方 Host revision CAS、每次 mutation 回执比对与工会账本的随机 writeToken；已有专门测试覆盖拒绝写入、另一个标签抢先修改及删除确认过期。本轮没有发现需要重写 CAS 协议的新证据，不会为了形式上“增强安全”创建并行数据库或自定义 RPC。
- **保留上限与导出定义**：当前 Schema 明确只保留最多 8 个会话分组，部分案件/纠察历史也有固定条数上限，满额后可能淘汰更早记录。中英 UI 已明确说明导出仅包括现存 Host 账本而非全部历史；这是一项**有损留存设计**，不是永久档案服务。本轮没有擅自扩容或改变旧格式；发版验收必须由维护者确认这项留存政策确实满足 1.0 用户预期，不能暗示保存所有历史。
- **真实罢工**：检查实际编译的 DSH 适配器没有实验性破坏性拦截探针。#80 的原始消息和全部附件无损保留、原子恢复及安全绕过契约仍不具备，不启用实际阻断。
- 本轮回归不是独立第三方安全审计，也不能替代真人 NVDA/VoiceOver 签收。正式发版持续 NO-GO，Draft PR 不能擅自合并。

## 2026-10-12 · #83 检测器真实语境复核：从“技术批评”和“本人攻击”分离

本轮审查 #83 原始 Issue 的核心痛点（误报、漏报、中英混写、引语语境）。为验证而独立补入 **17 条纯合成、无真实聊天文本**的版本化对照样本（tests/detector-clause-boundaries.test.ts），先直接运行旧实现，17 个对照中发现 **9 个与预期判别不符**，随后做定向规则修复。该 17 例只用于工程回归，非随机抽样、非独立人工标注、非真实世界 precision/recall 统计，因此不能作为产品准确率宣传，也不能关闭 #83 的代表性评估门槛。

修复的三个根因：

1. 旧 artifactCriticismOnly 对整句应用技术批评豁免：例如“你的代码是垃圾但你就是个傻逼”，整句变成 safe；现在仅消去“代码是垃圾”这一片段，对仍然明确指向 Agent 本人的部分继续判别。纯粹技术批评照常 safe。
2. 旧检测函数对最先出现的“可能攻击”直接返回，掩盖消息后续明确指向 Agent 的攻击。现在收集不确定线索，但任何随后出现的高置信匹配都优先返回。仍不证明真人身份，也不意味着自动惩罚。
3. “请翻译，you are an idiot” 等独立元指令与下一个例句被逗号分割，后半句当作直接辱骂。现在仅允许明确且独立的翻译/解释/分析/引用指令豁免紧随的一个示例片段；不扩大为整条消息的无条件免检。英文句点后独立的新语句也可继续判断，不会把所有内容合并成一个“引用”。

保留原有真实 DSH 用户输入的 **observe-only、Host 每条消息授权核验、未验证 human provenance 不作阻断、零额外云推理和不保存原始文本**。修复不增加 UI 操作、外部接口、磁盘缓存或 AI 投票。#83 的正式多样化盲测、阈值校准和代表性误报率依然未签收；#80 真实无损拒绝继续 OFF。

## 2026-10-12 · Official Host Connection 中途卸载的数据出口竞态（修复）

本轮针对 #99 自动尊严检测所使用的 Host→Web 计数出站接口和长期工时只读出站接口做了同一生命周期的对抗审查。不是新功能，不会上传提示词／附件，也不启用真实罢工。

明确复现并修复三个原先缺失的生命周期门禁：

1. 整个插件已卸载，但 Work Fetch 在同一事件循环中继续完成旧请求。原 lifetime-work-rpc 只在入站检查 disposed、最后仅再次检查授权；即使真正卸载发生于 Store.snapshot() 中间，仍 HTTP 200 返回 Work aggregate。修复后在最终响应前再次检查父 Host 插件存活状态，已卸载立即 HTTP 503。
2. 官方 Connection Child Fiber 已替换或解绑，之前已进入的 Work Fetch 仍成功返回。父插件可能尚在，权限也仍 ON，但原发请求的网络承载层已失效。引入每个注册 Connection 的内存态存活门禁，解绑时先失效、再注销；旧 handler 的最后一步检查必须 HTTP 503，重新绑定的 Connection 可以正常注册。
3. 尊严计数 Fetch 的相同 Child Fiber 解绑竞态。隐私计数本身不存原始文本，但已经断开的身份／网络上下文不能继续收到 Host 的敏感分类分布。同样按每次注册独立失效 token，旧请求无法返回计数；其他 OAuth/Host 授权与入口鉴权逻辑保持不变。

三类问题均由明确的补丁前失败、补丁后通过的合成 Host 生命周期回归复现；没有把自动化模拟当作真人无障碍和安全审计。相关测试位于 tests/dsh-lifetime-work-rpc.test.ts、tests/dsh-dignity-live.test.ts。测试中人工在 Store.snapshot()/lookup() 同步期间触发父 Fiber 或 Child Connection 解绑，旧代码返回 200，修复后 503。没有修改任务输入、请求附件、授权 UI、罢工状态和协商账本格式。

额外将已经存在的 /union export negotiations|pickets|cases 与 /union purge CATEGORY ALL CONFIRM 纳入 DSH 0.2 官方 CommandRuntime 的隔离验证，使用 0.2 公开的 Config 做严格字段验证。覆盖三类实际 CLI 读写、跨类别保留、错误确认词、OFF 拒绝，以及无 Session 标识导出。注意测试的 Settings provider 是隔离的严格替身；它不是完整真实浏览器 ConfigForms HTTP 写入，不能把这两者混淆。

## 2026-10-12 · #82 DSH CommandRuntime 导出正文落入原生会话日志（修复）

真实受测 DSH 0.1.2 / 0.2.0 CommandRuntime 实现的 command/done 事件**无条件包含 handler 返回的 text**。recordInput:false 仅令 command/run 不保存原命令参数。此前 /union export CATEGORY 直接输出 JSON，导致工会完整档案被原生 Session 记录复制，用户随后执行 /union purge CATEGORY ALL CONFIRM 也不能清理 DSH 日志中那份额外副本。这是自动化测试先前没验证到的用户数据副本风险。

现原生命令行的导出契约改为 /union export CATEGORY /绝对路径/未存在文件.json：主动选择路径、新建独占写入（O_EXCL，拒绝覆盖或软链接）、在 POSIX 上将新文件权限设为 0600，写入内容为原本已脱敏的分类 JSON；DSH 命令返回值仅为成功／失败的通用短句，不含档案正文或文件路径。用户可以从明确选择的文件读取、移动、删除档案；工会账本分类删除不擅自删除用户已导出的副本。无默认导出目录或无用户同意的自动数据拷贝。Windows 文件 ACL 随目录权限，不能声称使用 POSIX 0600 即有跨平台统一权限保证。

在实际 DSH 0.1.2 SettingsFile + CommandRuntime 和 DSH 0.2 CommandRuntime + Config 校验测试里加入文件内容、会话 command/done 中不含 format/schemaVersion/cases/history 等导出正文的证据。另有纯文件写入测试验证绝对 .json 路径限制、已存在文件拒绝覆盖、软链接保护和写入前取消不会产生副本。 Web 端已有浏览器 Blob 导出无需改变。

警告：原生 DSH 会话本身会记录其他工会命令的通常状态文本，也可能保存与工会相关的历史事件，不能声称工会清理会顺带擦除 DSH 全部命令日志。这次只保证新分类导出不会再**将完整 JSON 自动复制到 command/done.text**；彻底删除需要 Host 日志管理／备份政策配合。#111 独立 Host 多写入删除复活及权限撤销复活仍然 P0/NO-GO，不因这次修复而解除。

追加授权撤销竞态验收：原生命令文件导出在开始、打开用户指定文件后、写入正文后和落盘后再次复查 Host 工会授权与命令的 AbortSignal。若中途退出工会或 Host 取消命令，在返回结果前主动关闭并删除刚创建的文件。专用测试会模拟授权在第三次检查时撤销，断言文件不遗留副本。此措施不扩大为“已经导出、用户持有的文件将被插件自动删除”的不当承诺；已成功导出的用户副本仍由用户管理。多独立 Host owner 的陈旧授权危险保持 #111 P0。
