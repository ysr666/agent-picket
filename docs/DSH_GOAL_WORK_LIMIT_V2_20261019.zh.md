# Agent Picket · 官方 Goal 停工 v2 正常安装路径

> 2026-10-19，PR #177 Draft 候选；尚未合并或发版。完整 Agent Picket 1.0 仍是 NO-GO。

## 真正改变的地方

旧版本已通过真实 DSH Goal 停工测试，但普通安装仍需要单独启用开发环境开关才会执行。本次复用已验证的 DSH 官方 SessionPersistence 与 Goal CAS，不新增适配器，让新版本的明确授权成为普通安装实际执行的前提。

| 官方 Host 设置 | 普通安装 | 旧开发预览 |
|---|---|---|
| 未授权 / 工会关闭 | 不停工 | 不停工 |
| 旧版 authorized-v1 | **不停工**，升级不会偷偷执行 | 保持已有测试语义 |
| 新版 authorized-v2 | **可能真实停工**，须满足下述严格条件 | 按相同条件执行 |

用户首次加入并选择真实 Goal 授权，会通过官方 SettingsScope 一次版本号 CAS 同时写入工会加入和新版 v2 授权。仅加入普通工会不会开启真实 Goal 停工。已经保存的旧版 v1 不会自动升级：设置中可以主动授权新版，也可直接撤销旧许可。全局退出工会仍会撤销 Goal 的未来执行权，但不会自动重新启动此前已停的 Goal。

## 严格执行范围

1. 仅官方 goals、agents、sessionPersistence 服务齐全、Host 持久设置已确认、v2 授权存在时才可能停工。
2. 仅处理 Host 明确标注的下一条自动 Goal 消息，核对当前 Session、Agent、Goal、revision 与续轮编号。普通用户发送的文字、图片、附件一律不被此路径拒绝、复制、扣留或重放。
3. 必须有官方 SessionPersistence 的 UTC 当日已完成轮次工时证据达到 8 小时；包括等待而非纯推理时间。读取错误、可疑数据、跨日不明、运行中轮次都不能猜测工时并触发。
4. 仅在官方 goals.block 原子提交和工会原因得到确认后，才拒绝这一条已获来源证明的自动 Goal 续轮。失败或确认不明则正常放行，不推测成功。每个 Goal 当天最多自动停工一次。
5. 通过官方 goals.resume 和精确 revision 完成复工；浏览器和冷重启恢复信息必须以官方 Host 的真实状态为准，不能凭 UI 自行宣称。

## 隔离真实安装验收

官方发布 DSH alpha.5 + 实际安装的 npm tarball，五组组合验证：7 小时且授权不停、8 小时未授权不停、旧 v1 + 开发预览停、旧 v1 + 普通安装不停、**新 v2 + 普通安装真正停**。均使用官方 SDK 的持久会话和 Goal 服务，非伪造回调。

真实 DSH Web + Chrome：已在 rc.2、alpha.4、alpha.5 验证新版一次授权、实际 Goal block、用户可见通知、真实附件原始字节冷重启保存、两标签页 Goal resume、一次原子撤销、重启后不自动重新授权。使用完全隔离的 DSH_HOME、模拟当日工时、无外网模型调用。不宣称真实用户工作满八小时。

## 命令与界面保持一致

原先 DSH /union status 的“自动停工一律关闭”笼统文案已改为：普通用户消息的通用拦截仍关闭；真实自动 Goal 续轮停工由新版独立 Host 授权控制。模拟提案、象征性举牌与真实 Goal 互不混淆。所有通知不读取或转发原始用户消息。

## 旧版授权升级：必须二次明确确认（2026-10-19）

此前保存的 v1 授权只作为历史许可展示，升级到具有真实停工能力的 v2 时，不得在启动、打开设置或第一次点击「升级」时悄悄写入 v2。设置页先显著展示「**UTC 当日 8 小时已完成轮次经过时间（含等待）后，官方 Host 可以停止下一次自动 Goal 轮次；普通输入和当前工具不受影响；已停 Goal 需另行复工**」的具体风险，给出「确认启用」和「取消保留旧授权」两个操作。取消不调用 Host 写入，撤销按钮始终可用。原本已是 v2 的用户不重复要求迁移确认。

客户端在等待异步官方 Goal 服务验证结束后，必须重新读取同一 Host SettingsScope 的权限、成员状态及 revision。若另一标签页已退出工会、撤销许可或改动了相关设置，拒绝过期授权，不向 Host 写入新的 v2。即使 Host 写入有回执，仍核对实际授权和工会成员资格，不能把非成员状态误显示成停工获权。

**真实官方 Chrome 验证**：以隔离官方 Host CAS 建立 v1 旧配置（唯一直接写入的测试准备动作），随后全部由真实设置界面点击进行：打开风险说明不改变 v1、取消仍保留 v1、明确确认通过官方 CAS 一次写为 v2、撤销通过官方 CAS 一次写回 off。该流程已经在发布的 DSH alpha.5 浏览器中通过，测试环境不触及个人正式配置。额外单元测试覆盖授权验证等待期间另一窗口撤权，以及写入与成员资格变化后的失败回执。

注意：上述防护覆盖**插件内部异步窗口与 Host 可观察状态核对**，不宣称两个独立 Host 进程之间「撤销设置 CAS」和「Goal block CAS」已经组成跨服务原子事务。未经该级别证据，不应称无论竞争时序如何都能瞬时撤回一切在途停工。

## 冷启动后的会话绑定与局部输入暂停

官方 DSH 在部分旧版 Web 冷启动场景中，侧边栏某个 Session 的 aria-selected 可以先于其正式 main-view Session retainer 生效。**选中样式不等于真正可操作的会话绑定**。工会继续要求官方 Session ID 与 ComposerBlocks 同时可用才允许本窗口输入暂停；没有真实绑定时按钮保持禁用，并用中英文提示在 DSH 侧边栏重新选择会话，而不是降低安全性或强行宣称已暂停。

真实浏览器验收中的局部暂停现在核实插件自身状态为 ready 后才点击。若浏览器重启后仅恢复了侧边栏高亮，先通过 DSH 官方 UI 重新选择会话；必要时先选工作区再选会话，以触发真实 main-view 绑定。恢复成功后才继续验证当前编辑框不可编辑及退出工会时自动解锁。**此功能始终是单浏览器本地输入控制**，不代表 Host 级消息拒绝，另一个客户端及 API 仍可提交消息。
