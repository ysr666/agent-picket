# Codex Goal owner-boundary adapter: read-only v1 (2026-10-12)

## Native facts established on an isolated Codex 0.146.1 installation

`codex features list` reports `goals` stable/true. Official `codex app-server generate-ts --experimental` exposes `ThreadGoalGetParams`, `ThreadGoalSetParams`, `ThreadGoal`, and `ThreadGoalStatus`. In an isolated App-Server with a temporary `CODEX_HOME`, `thread/start` created a synthetic *idle thread*; a single App-Server **owner process** acknowledged `thread/goal/set` with status `paused`, then `thread/goal/get` returned `paused`; another set/readback returned `blocked` and emitted `thread/goal/updated`. No `turn/start` or cloud model prompt was submitted, no user's Codex profile was modified, and the private Goal objective was only synthetic.

**Do not exaggerate this experiment:** An isolated owner-state mutation is NOT evidence that an external process can atomically stop a running Codex Desktop thread, preserve in-flight tool work, suppress the next automatic Goal round, or durably resume its original content after an app crash. Codex 0.146.1 `ThreadGoalSetParams` contains `threadId`, optional `objective`, `status` and `tokenBudget`, but **no `expectedRevision`/CAS parameter**. A naive `get→set` can race with human resume, another window, or newly starting work. Do not wire it as a real Agent Picket strike without a separate, verified same-owner serialization and conditional transition contract. An experimental Goal screen or a new Task does not establish that contract.

## Implemented non-invasive adapter contract

`src/adapters/codex/goal-readiness.ts` defines `readCodexOfficialGoal` and `parseCodexGoalReadback` for the official `thread/goal/get` response. It verifies the exact requested thread ID, known official status, timestamps and nonnegative usage values. It NEVER copies private Goal objective text into its normalized readback, writes Host state, clears a Goal or intercepts prompts. Invalid, missing, spoofed or unavailable Host responses are `unconfirmed`, not permission to block.

`inspectCodexGoalHoldSafety` explicitly requires six independent facts: Host-authenticated real-strike consent, verified active App-Server/thread identity, **exclusive cross-process Goal ownership/fencing**, verified idle-after-current-turn and before-next-round safe boundary, conditional/serialized status transition, and proven durable lossless resume. The static `CODEX_0146_NATIVE_GOAL_CAPABILITY` does not assert these facts merely because `thread/goal/set` works, so automatic strikes remain DISABLED. `tests/codex-goal-readiness.test.ts` checks the privacy/readback/provenance safety contract.

## Outstanding for #119 and 1.0

Build an opt-in, official owner-process connection with verified Goal identity and Host revision fencing or equivalent linearizable serialization. Demonstrate at least one real native autonomous Goal's full tool/model Turn completing, its next round staying stopped, no content loss, user-visible notification, explicit resume, cold restart and more than one window, across Windows/macOS/Linux. Independently support first-run real-strike consent and an optional per-strike confirmation setting. Leave the existing Codex `UserPromptSubmit` Hook advisory-only and keep Hook trust enabled. The release gate stays NO-GO.

## 2026-10-13 · Official UserPromptSubmit refusal: native proof WITHOUT kernel/process interception

**Architecture correction:** a real **new-work refusal** is NOT the same capability as **pausing an already-running, cross-process autonomous Goal**. The latter still lacks official Goal CAS/owner fencing. Do **not** require kernel-level locks for the former, and do **not** manipulate Host internals, force-kill turns or rewrite Codex state to emulate a strike. Codex's supported `UserPromptSubmit` command hook has an official `{"decision":"block","reason":"..."}` response and can reject an incoming prompt before model dispatch. `PreToolUse` can separately refuse a pending tool call; neither promises to pause a current model Turn. No unauthorized prompt replay, attachment mutation or implicit resume.

A genuine **Codex CLI 0.146.1 ARM64 App-Server**, isolated disposable `CODEX_HOME`, localhost-only non-inference Responses sink, one synthetic prompt per run, and no user credentials/configuration provided direct evidence in `tests/codex-native-prompt-hook.real.test.ts`:

| Native official `UserPromptSubmit` outcome | Local model requests | Interpretation |
| --- | ---: | --- |
| Trusted hook returns `decision:block` | 0 | Real pre-model refusal; blocked new work |
| Trusted hook returns ordinary `{}` | 1 | Normal non-blocking execution path |
| Trusted hook exits with code 1 | 1 | **Fail-open on hook failure**, unacceptable to claim guaranteed protection |

The initial native test **failed**, revealing an important authorization boundary. Official `hooks/list({cwds:[temporaryRoot]})` reported `enabled:true` but `trustStatus:"untrusted"` and the model endpoint received a request. That is expected and safe Host behavior: enabled is NOT permission to execute an unreviewed user hook. `--dangerously-bypass-hook-trust` was tested but did not resolve that App-Server's trust state; the working native proof did **not** use it. Instead, the test inspected its own synthetic hook sourcePath/command/hash, issued **official** `config/batchWrite` to approve ONLY its disposable test hook's exact SHA-256 definition, re-read `hooks/list` to observe `trusted`, then retested block/allow/fail. **Do NOT copy that test-only automatic trust flow to user installation.** An actual user must authorize Agent Picket at first run AND review the exact non-managed hook using the Host's official `/hooks` trust workflow; a changed hook hash needs renewed Host review. If trust is unavailable, modified, disabled, malformed or unknown, Agent Picket cannot truthfully display a guaranteed active Codex strike.

`src/adapters/codex/prompt-hook-readiness.ts` contains **read-only** official `hooks/list` normalization. Its strict `canOfferOptInNewWorkRefusal` applies only to an exact trusted, enabled, expected per-definition handler with no errors; `failClosedOnHookErrorProven` is deliberately constant **false**. Pure negative tests reject malformed, duplicate, untrusted, modified, other-source, disabled and spoofed data. This readiness merely allows offering an informed opt-in, NOT activating a Host strike by itself. Production requires visible union announcement, explicit informed authorization, the exact Host-approved hook and an opt-out/resume setting, native cross-client tests, and an honest **degraded / cannot guarantee blocking** state when the hook isn't trusted or fails.

**Product direction:** prioritize Host-official, bounded and reversible **new-work refusal** first (user prompt and separate tool preflight); no kernel interception. Treat *current-turn safe completion* and *multi-owner live Goal hold/resume* as separate future Host API-dependent capabilities. The installed npm package still excludes `dist/adapters/codex/**`, so these tests DO NOT deploy a production Codex adapter. Overall release gate remains NO-GO.
